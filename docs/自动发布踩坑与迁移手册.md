# 小红书自动发布：踩坑总结与迁移手册

> 来源：2026-11-02 在 WSL2 + opencode Code Mode 环境下，用本地 `xiaohongshu-mcp` 连续发布两篇图文的实测记录。
> 目的：把这套流程搬到别的环境（CI、服务器、其他 agent 框架）时，能一次配对、少走弯路。

---

## 1. 运行架构（先搞清边界，很多坑都源于此）

```
Windows 桌面
  └─ WSL2 (本机)
       ├─ opencode ──(MCP over HTTP)──► xiaohongshu-mcp  127.0.0.1:18060
       │                                    └─ 内置 Chromium（无头）→ 小红书 web / creator
       ├─ data/cookies.json      # 登录态（v2 格式，含 seed）
       ├─ data/home/             # 进程专用 HOME，浏览器缓存、指纹 seed 依赖目录
       └─ logs/mcp.log
```

关键点：

- **MCP 服务只跑在 WSL 里**，用的是项目自带 Chromium，不读 Windows 浏览器的 cookie/profile。
  在 Windows 侧登录，对这边的发布**没有任何作用**。
- 每次工具调用都会**新起一个浏览器进程**：首屏加载 20–30s，发布完整流程实测量级 **2 分半**。
  因此客户端超时不要低于 180s。
- 会话由 `data/cookies.json` + `data/home` 里的指纹 seed 共同决定，**两者必须配套迁移**。

## 2. 本次实际遇到的问题（按出现顺序）

### P1. 标签联想点击失败（偶发）

```
发布失败: 小红书发布失败: 输入标签[Cloudflare]失败:
点击标签联想选项失败: 元素无可点击区域
```

- 触发场景：输入标签后，下拉联想项已经渲染但可点击区域为 0（渲染未完成/被遮挡）。
- 处置：**先查主页确认没有发出去**，再用完全相同的参数重试一次；本次重试即成功。
- 风险：如果直接盲重试，有概率产生重复笔记。自动化必须做「发布前快照 + 失败后核对」。

### P2. 创作者中心登录失效（核心坑）

```
发布失败: 创作者中心登录失效，请重新扫码登录
```

- 机制：发布走 `creator.xiaohongshu.com`，代码里会先访问创作者首页，等待
  `galaxy_creator_session_id` 这个 cookie 出现，最多等 15s（`xiaohongshu/creator_session.go`）。
- 现象：`check_login_status` 返回**已登录**（它只校验主站 `xiaohongshu.com/explore` 的 DOM），
  但 cookie 文件里根本没有 `galaxy_creator_session_id`。
- 也就是说：**主站登录态 ≠ 创作者中心登录态**，这是两套 cookie。
- 本次还观察到：21:46 发布成功，21:57 同一账号再发就失效了。会话可能在很短时间内过期，
  也可能被同一账号在其他网页端登录踢掉（README 里也提醒了这点）。
- 处置：不能靠主站状态判断，必须重新登录一次；登录后 `check_login_status` 只作辅助确认。

### P3. 「已登录」时拿不到二维码

- `get_login_qrcode` 在检测到主站登录时，直接返回「你当前已处于登录状态」，**不出二维码**。
- 所以 P2 场景下想重新扫码，必须先 `delete_cookies`（会删除 `data/cookies.json`），
  再 `get_login_qrcode`。删除后日志里会持续出现
  `failed to load cookies ... no such file or directory`，这是**正常噪音**，不是故障。

### P4. 二维码在 WSL + TUI 里看不到

- MCP 返回的是 MCP `image` 内容块（base64 PNG），opencode TUI 不渲染图片，用户只看到一行提示文字。
- 正确做法（项目里已有现成脚本，优先用）：

| 场景 | 命令 |
|---|---|
| 有 WSLg（Windows 11） | `./scripts/login.sh`，浏览器窗口直接显示到桌面，二维码自动刷新 |
| 无窗口/远程 | `./scripts/qr.sh`，生成 `data/login-qr.png` + 放大版 `login-qr-big.png` 并调 `explorer.exe` 打开 |

- `qr.sh` 内部用 zxing 解码原图、再用 `qrcode` 库以 `box_size=12` 重新渲染大图，
  比手工放大清晰得多。依赖在 `.venv` 里（pillow / qrcode / zxing-cpp / requests）。
- 若没有这些依赖，兜底方案：把原始 PNG 落盘到 `/mnt/c/Users/<用户>/Downloads/`，
  用最近邻放大 6 倍 + 加白边再 `cmd.exe /c start` 打开（本次就是用 Go 临时写的放大器救的场，
  效果不如 zxing 重绘）。

### P5. 二维码「扫了无效」——多半不是权限问题，而是过期

日志证据：

```
22:06:17 等待扫码登录，会话 #4，超时 4m0s
22:10:16 登录会话 #4 结束，未检测到扫码（超时或已被新的二维码取代）
```

- 有效期只有 **4 分钟**。
- **每取一次新码，旧码立即作废**（日志里的「已被新的二维码取代」）。
  本次排查时连取了 4 张，用户扫到的正好是最早那几张已作废的码，白折腾。
- 铁律：**只生成一次二维码，生成前先确认人已经在手机旁**；要重发就明说「旧码作废」，
  并给出新的到期时间，不要在后台反复轮询重取。

### P6. 扫码成功后的生效方式

- 扫码确认后，后台协程会把 cookie 写入 `data/cookies.json`。
- 本次实测：**不需要重启 MCP 服务**，直接调用发布即成功（浏览器实例在每次调用时重新加载 cookie）。
  但 README 建议重启，属于保守做法；如果你的版本 cookie 只在上层缓存，重启一次更稳。

### P7. `get_my_profile` 偶发 `context deadline exceeded`

- 发生在一次发布失败后紧接着调用时，浏览器进程尚未释放。
- 处置：重试即可（本次第二次即成功）；自动化里按「可重试」处理，并给 90s 以上超时。

### P8. 发布成功返回值里没有链接

- 成功返回形如：

```
内容发布成功: &{Title:... Content:... Images:1 Status:发布完成}
```

- 没有 note id，需要再调 `get_my_profile(tab=note)`，取 `feeds[0].id`，
  拼 `https://www.xiaohongshu.com/explore/{id}`。
- 判断成功的可靠依据：`Status:发布完成`，或服务端日志出现
  `发布成功，已跳转离开发布页 url="https://creator.xiaohongshu.com/publish/success..."`。

### P9. 参数层面的硬约束

| 项 | 约束 | 本次实测 |
|---|---|---|
| 标题 | ≤ 20 个中文字/英文单词 | `前云厂商销售，说点AWS大实话` 通过 |
| 正文 | 不含 `#话题`，标签单独走 `tags` | 783 字通过 |
| 图片 | WSL 绝对路径，不要中文文件名 | `assets/covers/cover-b.png` 通过 |
| 正文换行 | 会被原样保留 | 短段落效果正常 |

## 3. 自动化落地 SOP（重点）

### 3.1 发布幂等（防重复发帖）

```
1) 发前快照：get_my_profile(tab=note) → 记录现有 (id, title) 集合 S
2) 调 publish_content
3) 若报错：
   a. 先 get_my_profile 再取一次集合 S'
   b. 若 S' 里出现目标标题 → 视为成功（只是返回体丢了），直接取链接
   c. 若未出现 → 按错误类型决定是否重试
4) 成功后同样用 S' 取 id 拼链接
```

### 3.2 错误分类与处置

| 错误 | 可自动重试 | 处置 |
|---|---|---|
| `点击标签联想选项失败: 元素无可点击区域` | 是，最多 1 次 | 重试前先做 3.1 的核对 |
| `创作者中心登录失效，请重新扫码登录` | 否 | 人工介入：`delete_cookies` → 出一次二维码 → 扫码 |
| `context deadline exceeded` | 是 | 提高超时（≥90s）后重试 |
| 标题/图片/描述校验失败 | 否 | 修内容，不要重试 |
| `没有捕获到 feeds 数据`（列表类） | 是 | 重试一次，搜索接口更稳 |

### 3.3 超时与并发

- 单次工具调用：建议 **180s**（发布含上传，实测 ~143s）。
- **不要并发调用**：每个调用会新起浏览器，机器扛不住，且容易互相干扰登录态与截图定位。
- 失败后至少间隔 5s 再重试，给旧进程释放时间。

### 3.4 登录态运维

- 发布前先 `check_login_status`，但它**不能代表创作者中心可用**（见 P2）。
  低成本探针：直接试发布一条草稿属性内容，或先调一次 `get_my_profile` 观察是否 200。
- 定期备份 `data/cookies.json` + `data/home`（seed 配套），这是最省事的迁移单位。
- 迁移到新环境时，**不要只拷 cookies.json**：seed 不匹配会被判定异常会话，
  表现为能查列表但发布失败或频繁掉登录。

## 4. 迁移到其他环境的检查清单

- [ ] 服务能起：`./scripts/start.sh`，`ss -ltnp | grep 18060`
- [ ] 依赖浏览器已就位：`data/home/.cache/xiaohongshu-mcp/`（首启约 148MB，SHA256 校验）
- [ ] `COOKIES_PATH`、`HOME`、`XDG_CACHE_HOME` 三个环境变量与本项目 `scripts/env.sh` 一致
- [ ] cookie 与 seed 成套迁移，或在新环境完整扫码一次
- [ ] 客户端 MCP 地址：`http://127.0.0.1:18060/mcp`，`Accept` 带 `application/json, text/event-stream`
- [ ] 超时 ≥180s，串行调用
- [ ] 图片路径为**该环境的**绝对路径（Windows 侧跑就换 Windows 路径）
- [ ] 时区正确（二维码有效期按本地时间算）
- [ ] 有一个能展示二维码的通道：WSLg / `explorer.exe` / 自建图片服务 / 人工传图

## 5. 命令速查

```bash
# 启停与状态
./scripts/start.sh            # 无头启动
./scripts/start.sh --headed   # 带窗口（WSLg）
./scripts/status.sh
./scripts/stop.sh

# 登录
./scripts/login.sh            # 有图形界面，推荐
./scripts/qr.sh               # 无窗口，落盘 + 自动打开
# 已登录但需要重登：先调用 MCP 工具 delete_cookies，再走上面两条之一

# 日志
tail -f logs/mcp.log
grep -E "发布成功|登录会话|发布内容失败" logs/mcp.log

# 本地 HTTP API（调试用，与 MCP 同一进程）
curl -s http://127.0.0.1:18060/api/v1/login/status
curl -s http://127.0.0.1:18060/api/v1/login/qrcode   # 注意：每调一次旧码作废
curl -s -X DELETE http://127.0.0.1:18060/api/v1/login/cookies
```
